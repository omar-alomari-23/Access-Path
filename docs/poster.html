Introduction & SDG 11 Alignment
11
SDG
SDG 11.2 — Safe, Accessible & Sustainable Transport for All Conventional navigation tools optimise for time/distance and ignore real-time accessibility barriers. AccessPath targets the missing trust layer: community-verified, time-sensitive data for wheelchair users, low-vision pedestrians, elderly individuals, and caregivers.

Urban infrastructure presents persistent barriers — broken ramps, blocked crossings, unlit paths, no-shade corridors — yet no real-time, community-driven tool exists to surface them reliably. AccessPath closes this gap with a crowdsourced reporting pipeline, community voting, moderator review, and confidence-scored route guidance.

Core innovation — "the trust loop": raw community submissions pass through duplicate detection, AI-assisted classification, community voting, and moderation to become verified, time-sensitive barrier data that meaningfully influences route suitability scores shown to navigators.

M1 Evaluation — Problem & Prototype Fit
M1 problem: urban navigation tools fail accessibility needs — no real-time barrier data, no community verification, no trust mechanism to distinguish current from stale hazards.
✓
Trust loop works end-to-end. Reports flow: submit → duplicate-check → AI classify → community vote → moderate → confidence-weighted route suitability. All stages are functional and pass 312 tests. The core M1 value proposition is delivered.
✓
Live barrier warnings on routes. RoutingService queries verified reports within 50 m of the route origin. Barrier data is real and current — even though path geometry is a hardcoded demo stub (full graph routing was out of sprint scope).
⚠
Routing geometry is not real. Full graph-based routing (OSRM / OpenRouteService) requires substantial integration effort beyond the 3-week window. Path geometry is hardcoded; suitability scores and confidence warnings are computed from live data. Users see valid barrier warnings on a simulated path.
⚠
"AI" classification scoped down. Delivered as deterministic keyword-bag matching (45 terms/category, 3 severity tiers). Zero external dependency; fully auditable and reproducible. Not machine learning, but it honestly fulfils the classification role within prototype constraints.
✕
GPS input and mobile layout absent. Reporters must manually type coordinates; the layout is desktop-first. Both directly contradict the M1 goal of improving field mobility for accessibility-constrained users.

M3 Design → M4 Implementation: Applied, Adapted & Evaluated

Architecture faithfully implemented. The layered client–server model from M3 (React/Leaflet → Spring Boot REST → PostgreSQL/PostGIS) was realised as designed. Controllers → Services → Repositories separation enabled clean unit-testability — 7 service classes covered by JUnit 5 + Mockito. 10 Liquibase changesets (001 = CREATE EXTENSION postgis → 010 = test account password fix) version-control every schema change. JWT + BCrypt enforced at both Spring Security filter level and @PreAuthorize annotations — dual-layer RBAC. Vite 7 was chosen as the frontend build tool: native ESM-based HMR gives near-instant hot reloads, critical when iterating on a complex Leaflet map UI. Vite's dev server defaults to port :5173 (the M3 spec had assumed :3000 from Create React App); the backend Spring Boot API runs on :8080. This port mismatch was the direct root cause of the CORS discovery documented below. Plain React useState and CSS handle all forms and styling — no component library was installed.

Key Deviations from M3 Plan

⚠ Classification redesigned: M3 described "AI core / keyword scoring." Delivered as ClassificationService — a static Map<String,List<String>> with 5 categories (STEP_FREE_ISSUE, SURFACE_HAZARD, OBSTRUCTION, LIGHTING_ISSUE, HEAT_NO_SHADE) × ~9 keywords each (45 terms total). Word-boundary regex avoids partial matches. suggestCategory() and suggestSeverity() (HIGH / MEDIUM / LOW keyword tiers) pre-fill the form. getConfidenceFlag() returns true if ≥2 total matches — triggers "High confidence" UI banner. Zero ML, zero external API. 16 unit tests, all PASS.

⚠ Routing geometry is a stub: getDemoRoutes() returns 3 hardcoded RouteOptions. Waypoints: arithmetic midpoint. ETAs: accessible=12 min, shorter=8 min (hardcoded). calculateSuitability(): accessible starts 0.8, non-accessible 0.5; −0.1 per warning; +0.2 if avoidStairs flag set. Warnings are live: getWarningsForRoute() calls reportRepository.findVerifiedNearby(lat,lng,50.0) — real PostGIS spatial query. 14 unit tests PASS.

⚠ Duplicate threshold asymmetry: Frontend: |ΔLat|<0.003°≈333 m non-blocking modal. Backend: ST_DWithin(location, point, 50.0) — throws IllegalStateException if duplicate within 50 m. Not specified in M3; discovered in integration testing. Intentionally layered — frontend gives soft early warning, backend is the authoritative rejection boundary. Documented in README.

⟳ Confidence formula — critical evaluation: The 7-day freshness decay (1.0→0.1) is the most debatable weight. A VERIFIED report with 10 CONFIRM votes that is 8 days old scores ≈0.82 — correctly surfacing trustworthy but potentially stale data. However, the 7-day cliff may be too aggressive for physically permanent barriers (a broken elevator awaiting council repair can stay unresolved for months). A future refinement would make TTL configurable per category: longer for structural barriers (e.g. 30 days), shorter for temporary obstructions (e.g. 3 days).

Technical Discoveries During M4 Sprint

☕ Java 25 → 17 LTS JAVA_HOME
Team configured Java 25 (latest available). Spring Boot 3.2 refused to start — Lombok and annotation processors are not certified for non-LTS Java 25. Fix: export JAVA_HOME=$(/usr/libexec/java_home -v 17). Downgrading to Java 17 LTS (minimum for Spring Boot 3.2) resolved all startup failures immediately. Lesson: always pin to LTS releases in annotation-heavy codebases.
🗄 PostGIS in changeset 001
Initially assumed PostGIS required manual Docker setup (psql -c 'CREATE EXTENSION postgis'), making environments non-reproducible across team. Discovered Liquibase supports raw SQL — CREATE EXTENSION IF NOT EXISTS postgis; placed in changeset 001 (first migration). Full DB setup now automated from clean container; changesets 001–010 cover all schema changes end-to-end.
⚠ Axios CORS + Spring Security Config Gap
The M3 API spec did not document CORS header requirements for Spring Security. During integration, Axios requests were blocked by the browser with CORS errors until Spring Security's CorsConfigurationSource was explicitly configured to allow the Vite dev server origin (http://localhost:5173). Only discovered when the frontend first called a protected endpoint. Lesson: API specifications must include security header requirements, not just endpoint contracts.
🖥 Laptop vs. Desktop: 125–150% DPI
Testing across team hardware: 125–150% browser DPI scaling (typical on modern laptops) caused UI element overlap and text truncation compared to desktop monitors. Leaflet click detection also misaligned at non-standard zoom — map pins unresponsive to direct click. Prototype 2 must be explicitly tested at 100–200% zoom and multiple DPI settings to meet SDG 11 accessibility requirements.

M3 Design Reflection

✓
Technologies were appropriate. Spring Boot + React + PostGIS matched team skills, supported geospatial queries, and enabled clean testability within sprint constraints. Monolith over microservices was the right call for a 3-week window.
✓
Trust-loop feature focus was correct. F-3, F-8, F-12, F-14, F-16 form the system's differentiator. All delivered. Without these, AccessPath would be no different from a static map.
⚠
"AI core" framing was imprecise. M3 should have stated "deterministic keyword matching" to avoid scope misalignment. The phrase "AI classification" created false expectations — honest re-labelling (45-term keyword-bag, 3 severity tiers) is a better description of what was built.
✕
Field usability was under-scoped in M3. GPS input and mobile-responsive layout were absent from the M3 prototype feature list despite being essential to reporter (P3 Khalid) and navigator personas operating in the field with a mobile device. The gap between "accessibility platform" mission and desktop-only delivery is the starkest disconnect between the M1 problem statement and Prototype 1's actual usability. A focus-visible CSS patch (extending keyboard outlines from buttons only to all focusable elements, including the Leaflet map wrapper) was merged as a late improvement — demonstrating responsive iteration even within the prototype sprint.

Why Python for integration testing? Python (standard library only, no extra packages) was chosen for the integration runner over a Java HTTP client test suite because it could be run by any team member without JDK setup, and its output is readable without IDE tooling.

Why manual frontend testing? Automated component testing (Jest + React Testing Library or Cypress) required mocking the Leaflet map component and Spring Security endpoints — too complex to set up within the sprint window. Structured manual test cases (documented with steps and expected outcomes) were used instead across all 6 pages, providing sufficient coverage for a prototype.

Coverage: 7 service classes · 5 controllers · scheduler · JWT security · @ValidCoordinates · exception handler · all 11 REST API groups.

⚠ Discovery: seed reports with expires_at in March 2026 expired immediately on startup. Documented in README with DB reset procedure.

Security implemented: Spring Security + JJWT (24 h token expiry) · BCrypt password hashing (rounds=10) · @PreAuthorize RBAC enforced at controller level for all MODERATOR-only endpoints · CORS configured per-origin for Spring Security · parameterised JPA/PostGIS queries throughout — no raw SQL string concatenation, preventing SQL injection. Security was not in scope for explicit test cases but is structurally enforced.

Prototype 2 — Vision for Second Iteration
Goal: close the three critical gaps — real routing, field-ready input, genuine intelligence — to transform AccessPath from a trust-layer proof-of-concept into a usable mobility tool.
🗺 Real Graph Routing
Integrate OSRM or ORS with PostGIS spatial queries. Preference filters (avoid stairs/inclines) drive real path computation, fully delivering F-1 and F-2.
📍 GPS + Click-to-Pin
Replace manual lat/lon entry with GPS geolocation and map-click capture. Critical for field reporters (P3 Khalid) and mobile navigators. Add Nominatim geocoding for address/place search — GPS solves origin input, but route destination input also requires address lookup since users cannot reasonably know destination lat/lng.
📱 Mobile-First PWA
Rebuild as Progressive Web App with large touch targets and offline caching. Test across 100–200% browser zoom and DPI scaling settings to address laptop/desktop gap.
🤖 ML Classification
Replace keyword matcher with a lightweight text classifier (DistilBERT or TF-IDF + logistic regression). Handles typos, novel phrasing, and reduces moderator burden.
📊 Analytics Dashboard
Heatmap + time-series views of barrier density for UG-4 (Urban Planner). Supports evidence-based SDG 11 infrastructure intervention.
🖼 Photo Attachments
Visual evidence for moderators, reducing false positives and triage time. Strengthens community trust in the data.

Team & Individual Development Process (M4)
H
Horizontal layer split — not vertical. The team divided by layer: a backend sub-team owned all Spring Boot services, controllers, repositories, and unit tests; a frontend sub-team owned all React pages, Leaflet integration, and forms. The rationale was specialised skill sets — team members were more confident in one layer than the other. While this aligned with individual strengths, it was the wrong structure for a 3-week sprint.
!
Retrospective: horizontal split created avoidable blocking. Frontend integration-testing could not begin until backend endpoints were stable, stalling work for several days. Vertical slicing — each member owning a complete feature slice from API to UI — would have eliminated these serial dependencies and enabled parallel progress on independent features. For Prototype 2, the recommended approach is feature-based ownership with a shared API contract document agreed upfront, so each member can deliver an independently testable vertical slice without waiting on others.
C
Coordination approach. Work was tracked via Git branch per feature; regular syncs resolved integration points — API contract changes, JWT token structure, coordinate precision across services. The Python integration runner acted as a shared integration test harness that any team member could run to verify API compliance across layers. The 61/61 pass rate confirmed clean inter-service boundaries when final integration was performed.
✓
Individual processes → group outcome. Persona ownership from M2 (P1–P7 assigned per person) carried forward into M4: the team member who defined a persona's requirements in M2/M3 was responsible for the frontend/backend work serving that persona's flows. This maintained traceability from requirements through to implementation and testing.
✕
Significant technical challenges. (1) Java 25 incompatibility — startup failure resolved by downgrading to Java 17 LTS. (2) PostGIS assumed manual setup — resolved by moving CREATE EXTENSION into Liquibase changeset 001. (3) Axios CORS configuration gap — Spring Security required explicit CorsConfigurationSource setup not documented in M3's API spec; discovered during integration week and fixed by whitelisting the Vite dev server origin (:5173). (4) Frontend automated testing infeasible — Leaflet map mock complexity led to structured manual testing. (5) Laptop/desktop zoom differences — UI overlap at 125%+ DPI scaling revealed need for responsive accessibility testing. (6) Seed data expiry — test reports set to expire in March 2026 triggered immediately on startup.
Conclusion: AccessPath demonstrates that a crowdsourced accessibility trust layer is technically achievable in a student sprint. The core loop — report → vote → moderate → route confidence — works end-to-end, backed by 312 tests. The main gap between plan and delivery lies in the sophistication of "intelligent" components (keyword matching vs ML, hardcoded vs real routing) — honestly documented and a sound foundation for Prototype 2.
